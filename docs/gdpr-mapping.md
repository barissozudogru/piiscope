# GDPR Mapping

This document maps the features of the privacy risk detection
application to the key principles of the **General Data Protection
Regulation (GDPR)** and the rights of the data subject.  The mapping
helps demonstrate compliance and provides guidance on how the tool can
be used responsibly.

## Principles relating to processing

The GDPR sets out six core principles in Article 5.  Controllers are
responsible for complying with these principles and must be able to
demonstrate their compliance.

| Principle | GDPR reference | Implementation in this application |
|-----------|---------------|----------------------------------|
| **Lawfulness, fairness and transparency** | Art. 5(1)(a) - personal data must be processed lawfully, fairly and in a transparent manner. | The application does not itself determine the legal basis for processing; that remains the controller’s responsibility.  However, it promotes fairness and transparency by providing clear documentation on what data is analysed, the purpose of the scan and how the findings are used.  Administrators can include a custom “legal basis” note in generated reports.  The UI surfaces privacy notices and consent statements where appropriate. |
| **Purpose limitation** | Art. 5(1)(b) - data must be collected for specified, explicit and legitimate purposes and not further processed incompatibly. | The system is designed solely for risk detection and remediation.  Raw data is not repurposed or shared with third parties.  Profiles define exactly which types of data will be analysed.  Findings are used only to drive remediation and reporting and are deleted after a configurable retention period. |
| **Data minimisation** | Art. 5(1)(c) - data must be adequate, relevant and limited to what is necessary. | Only metadata (row index, column name, rule ID, severity, confidence and evidence sample) is stored by default.  Raw data is never persisted unless a Super Admin explicitly enables encrypted storage for a limited duration.  The detection engine processes data in streaming mode and discards the input after scanning.  Profiles allow users to narrow the scope of detection to specific columns or patterns. |
| **Accuracy** | Art. 5(1)(d) - personal data must be accurate and kept up to date; inaccurate data must be erased or rectified without delay. | The application supports the right to rectification by allowing controllers to identify inaccurate personal data (e.g., mis-detected entities) and correct them in the source dataset.  A false-positive review queue highlights uncertain findings. |
| **Storage limitation** | Art. 5(1)(e) - data should be kept no longer than necessary. | Configurable retention policies enforce deletion of findings after N hours or days.  Raw files can be processed in a stream-only mode that never writes them to disk.  The audit log is append-only but can be pruned in accordance with legal retention requirements. |
| **Integrity and confidentiality** | Art. 5(1)(f) - data must be processed securely using appropriate technical and organisational measures. | The backend enforces encryption in transit (HTTPS) and at rest (AES-256 via environment-derived keys).  User authentication uses salted password hashes and JWT tokens.  RBAC ensures that only authorised users can access sensitive results.  The detection engine runs locally and does not send data off-premise. |
| **Accountability** | Art. 5(2) - controllers must be able to demonstrate compliance. | The application records an immutable audit log of all actions (scans, exports, profile changes, logins).  Reports include references to the selected legal basis and the detected data categories.  This evidence can support DPIAs and internal audits. |

## Rights of the data subject

The GDPR grants several rights to individuals whose data is processed.
Controllers must be able to respond to these requests.  The
application provides tooling to assist but does not replace the
controller’s obligations.

| Right | GDPR reference | Support in this application |
|------|---------------|-----------------------------|
| **Access** | Art. 15 - the data subject has the right to obtain access to their personal data. | Reports generated by the system include samples of detected data and can be supplied to data subjects to show what information about them is held.  Because only metadata is stored, access requests can be satisfied without revealing full raw datasets. |
| **Rectification** | Art. 16 - the data subject can have inaccurate personal data corrected. | Users can edit incorrect or false-positive findings via the false-positive review queue.  After updating the source data, a re-scan will reflect the rectification. |
| **Erasure (right to be forgotten)** | Art. 17 - the data subject can request deletion of their personal data. | The system supports deletion at two levels: (i) individual findings can be purged and (ii) entire scan jobs and their associated metadata can be removed.  When raw data storage is enabled, Super Admins can trigger secure deletion (wiping) of files upon request. |
| **Restriction of processing** | Art. 18 - individuals can request that processing be restricted under certain conditions. | Scan jobs can be paused or cancelled.  Administrators can flag certain rows as out-of-scope, preventing further analysis or remediation.  A restricted processing flag is stored alongside findings to prevent their use in exports. |
| **Data portability** | Art. 20 - data subjects can receive personal data in a machine-readable format and transmit it to another controller. | The export functionality allows controllers to generate a CSV or Parquet file of the data subject’s records after remediation.  The file is machine-readable and includes provenance metadata. |
| **Objection** | Art. 21 - individuals have the right to object to processing for reasons related to their particular situation; they can object to direct marketing at any time. | If a data subject objects, controllers can halt scans or exclude their records from analysis.  Profiles include a suppression mechanism to blacklist specific identifiers.  The application is not used for marketing activities. |

## Notes on special categories and legal basis

Article 9 prohibits processing of special categories of personal data
(health data, genetic data, etc.) unless specific legal grounds exist.
The application’s **Medical/PHI** profile is intended for controllers who
already have a lawful basis (e.g. patient care or public health).  Users
must ensure that they have obtained valid consent or rely on another
lawful basis before scanning special categories of data.  The tool
assists with data minimisation, security and accountability but does
not itself confer a legal right to process sensitive data.
